# GarageOS Communications Platform — Product & Architecture Reference

> **Status: product/architecture reference for implementation planning. Not a drop-in implementation spec.**
>
> Before changing code, audit the current GarageOS repository, database schema, domain model, permissions, tenant isolation, existing Resend/Twilio integration, domain onboarding, booking, appointments, quotes, invoices, reminders, existing email components, and current admin UI. Reuse and extend sound code instead of creating parallel systems.
>
> Also inspect the Messages module in the Montreal Spider Co. repository as a UX/architecture reference for: contact-form inbox, replying to stored messages, composing a new email, selecting an actual configured sender identity, rendering a branded preview, and recording replies. Do **not** blindly port it. GarageOS must be multi-tenant and substantially more complete.
>
> The intended workflow for Claude (or any future developer) is: **audit current state → identify reusable pieces → propose implementation plan and migrations → implement in stages.**

---

## 1. Product principle

GarageOS should let an independent garage run customer communication without leaving the platform.

The product vision is not "send a few notification emails." Communications is a first-class GarageOS module that connects directly to the rest of the operating system:

```text
Clients + Vehicles + Appointments + Quotes + Work Orders + Invoices
                              ↓
                   GarageOS Communications
                              ↓
          Inbox + Automations + Campaigns
                              ↓
                    Email + SMS delivery
```

For a typical small garage, GarageOS should remove the need for a separate transactional-email tool, a separate customer inbox for GarageOS-originated conversations, and in many cases a separate newsletter/campaign product.

Core surfaces:

1. **Inbox** — human 1:1 customer communication.
2. **Automations** — operational messages generated by business events.
3. **Campaigns** — legitimate 1:many newsletters, seasonal outreach, retention, and service-related marketing.
4. **Templates & Branding** — common rendering, shop identity, language, footer, and controlled message templates.
5. **Sender Identities & Routing** — real provider-backed sender configuration.
6. **Usage, Consent & Deliverability** — quotas, suppression, logs, abuse controls, and compliance.

All of this is multi-tenant. A shop must never see, use, or send through another shop's identities, messages, clients, domains, phone numbers, usage, or templates.

GarageOS owns the orchestration and application state. Resend, Twilio, or future providers are transports, not the source of truth.

## 2. Existing GarageOS code is the starting point

At the time this document was consolidated, GarageOS already contains meaningful pieces of the desired system, including:

- Resend-backed transactional email.
- Twilio-backed SMS.
- Appointment confirmations/reminders/cancellations.
- Invoice and quote delivery.
- Service reminders.
- React email components for appointments, invoices, quotes, accounting, and reminders.
- `src/lib/email-config.ts` channel-based routing.
- `src/lib/email.ts` and `src/lib/sms.ts`.
- `src/lib/appointment-notify.ts`.
- Shop-level email/contact configuration.
- `EmailRoutingPreview`.
- Domain settings/actions and domain helpers.
- A domain migration and current domain-related UI.
- Shop slug / booking presence.
- Existing send timestamps and counters on some business entities.
- Roadmap direction toward a reliable outbox.

Before introducing new models or services, inspect these paths and determine what should be generalized, migrated, deprecated, or retained.

A likely target flow is:

```text
Business event OR human compose action
                ↓
GarageOS communications service
                ↓
Shop + user permissions + entitlement + consent
                ↓
Communication route / sender identity
                ↓
Template or free-form body + shared renderer
                ↓
Message / outbox record
                ↓
Provider adapter
        ├── Email → Resend
        └── SMS   → Twilio
                ↓
Provider webhooks / inbound events
                ↓
Delivery state + inbox/history + usage ledger
```

Do not add abstraction merely for architectural aesthetics. Introduce it where it gives GarageOS a single source of truth, safer tenant isolation, reliable retries/idempotency, observable delivery, reusable rendering, and one foundation for Inbox/Automations/Campaigns.

## 3. Onboarding: business identity, domain, web presence, and communications

Communications starts during shop onboarding, but onboarding choices must **not** be permanent.

GarageOS should explain that the user can change these settings later under an appropriate Settings area such as **Domains & Communications**.

### 3.1 Ask whether the shop already owns a domain

During onboarding:

```text
Do you already own a domain for your garage?

[ Yes, connect my domain ]
[ No, use GarageOS for now ]

You can change this later in Settings.
```

### 3.2 Shop already owns a domain

GarageOS should offer to connect the domain without forcing a registrar transfer or nameserver transfer.

The implementation should request only the DNS records required for the features the shop enables, for example:

- Website / public landing routing.
- Email sending verification.
- Inbound mail if/when that domain is used by the GarageOS Inbox.

Do not overwrite an existing root website by default. If the shop already has a website, GarageOS can still use a booking subdomain, hosted landing subdomain, or communications-only configuration.

The domain settings already present in GarageOS must be audited and reused rather than rebuilt from scratch.

### 3.3 Shop does not own a domain

The shop should still get a complete GarageOS identity immediately.

Example product concept:

```text
Public presence:   garage-tremblay.garageos.com
Managed email:     garage-tremblay@clients.garageos.com
Booking:           same shop slug / GarageOS presence
```

The exact managed sending domain must be chosen based on current provider behavior and DNS/deliverability constraints.

### 3.4 Exact-domain verification caveat

Do not assume that verifying `clients.garageos.com` automatically permits sending from arbitrary nested tenant subdomains such as:

```text
service@garage-tremblay.clients.garageos.com
```

Provider rules must be verified at implementation time.

For a first reliable version, identities such as these may be operationally simpler:

```text
garage-tremblay@clients.garageos.com
garage-tremblay-appointments@clients.garageos.com
garage-tremblay-invoices@clients.garageos.com
```

If GarageOS later automates provider provisioning/verification for per-shop nested subdomains, the product can move to prettier tenant-specific addressing without changing the higher-level identity model.

### 3.5 Business identity should be reusable across the platform

The shop identity should eventually feed both Presence and Communications:

- Shop name.
- Logo.
- Phone.
- Address.
- Website.
- Domain.
- Language defaults.
- Public contact form.
- Booking.
- Email branding.
- Sender display names.

Changing a shop's identity should update the appropriate downstream surfaces without duplicating values across unrelated settings.

## 4. Sender identities: real infrastructure, not cosmetic settings

GarageOS must have a real model for approved sending identities.

Conceptual model:

```text
SenderIdentity
  id
  shopId
  type                GARAGEOS_MANAGED | CUSTOM_DOMAIN
  address
  displayName
  domainId?
  status              PENDING | ACTIVE | SUSPENDED | FAILED
  verifiedAt?
  createdAt
  updatedAt
```

Exact Prisma names are up to the implementation after schema audit.

### 4.1 Never accept arbitrary From addresses

The admin must never be allowed to type any arbitrary address into a `From` field and have GarageOS attempt to send it.

Any selectable sender must:

- belong to the current `shopId`;
- be authorized by GarageOS;
- be active/verified;
- be permitted by the shop's plan;
- map to real provider-capable infrastructure.

This prevents spoofing, cross-tenant abuse, and confusing provider failures.

### 4.2 Sender routing must control the actual delivery origin

A configuration screen may show, for example:

```text
Appointment confirmations → Appointments sender
Appointment reminders     → Appointments sender
Quotes                     → Estimates sender
Invoices                   → Billing sender
Service reminders          → Service sender
General Inbox email        → Service sender
Campaigns                  → Marketing sender
```

Conceptually:

```text
CommunicationRoute
  shopId
  event / purpose
  senderIdentityId
```

The critical invariant is:

> **The sender selected in GarageOS settings must be the sender identity actually passed to the delivery provider for the next applicable message.**

Do not leave per-shop routing as cosmetic database metadata while an environment variable silently determines the real `From`.

Environment variables may define platform defaults/infrastructure, but tenant business configuration should resolve from GarageOS application state.

### 4.3 Managed and custom-domain identities use the same routing engine

The downstream sending path should not care whether an active identity is:

```text
garage-tremblay-invoices@clients.garageos.com
```

or:

```text
billing@garagetremblay.ca
```

Both should resolve through the same `SenderIdentity` / route abstraction.

### 4.4 Anti-abuse: identity mutation vs route reassignment

Creating or renaming senders is sensitive. Reassigning an event to another already-approved identity is not equivalent.

For **identity creation/rename**, consider:

- OWNER-only permission.
- Reauthentication for sensitive changes.
- Reserved names (`garageos`, `admin`, `security`, `postmaster`, etc.).
- Per-plan alias/identity limits.
- Creation/rename rate limits.
- Cooldown after repeated renames.
- Audit log.
- Keeping an old address as a temporary receive alias when practical.

For **route reassignment**, allow reasonable flexibility because both identities are already trusted.

## 5. Shared email renderer, branding, signature, and footer

Every GarageOS-generated customer email must pass through a shared rendering/layout layer.

Do **not** duplicate headers and footers independently across Appointment, Quote, Invoice, Inbox, Campaign, Reminder, etc.

Conceptually:

```text
ShopEmailLayout
  shop branding/header
  message body
  optional human signature
  shop identity/footer
  Powered by GarageOS
  compliance block when applicable
```

The implementation may use another name, but there should be one reusable rendering contract.

### 5.1 Branding

Use shop-level data such as:

- Logo.
- Shop name.
- Contact phone.
- Address.
- Website/domain.
- Optional safe accent color/theme if GarageOS supports it.
- Preferred/default language.

### 5.2 "Powered by GarageOS"

Customer-facing email produced by the platform should include a discreet **Powered by GarageOS** platform attribution according to product/plan rules.

This should be centralized in the renderer so it cannot be forgotten by individual templates.

### 5.3 Signature is not the same thing as branding/footer

Human 1:1 email can include a signature, for example:

```text
Thanks,
Jean Tremblay
Service Advisor
```

Then the shared shop footer follows.

Conceptual priority:

1. User-specific signature if enabled.
2. Shop default signature fallback.
3. No human signature for purely automated system messages unless product design calls for one.

The signature must not be able to remove or override required branding/compliance elements.

### 5.4 Global template migration requirement

When Claude implements the shared renderer, audit **all existing GarageOS email templates** and migrate them to the common layout in the same communications initiative unless there is a documented reason not to.

This includes existing appointment, invoice, quote, receipt/accounting, reminder, and future Inbox/Campaign emails.

The goal is consistent branding from day one, not a mixture of legacy and new layouts.

## 6. Inbox is a first-class product surface

Inbox is **not** merely a future idea. It is part of the target communications module.

The UX should borrow useful concepts from Montreal Spider Co.'s Messages admin:

- stored contact-form messages;
- reply in context;
- compose a brand-new email;
- selectable real sender identity;
- branded preview;
- reply history;
- delivery feedback.

GarageOS must extend this for multi-tenant shop operations.

### 6.1 Inbox capabilities

Target basic email capabilities:

- Conversation/thread list.
- New/unread state.
- Search.
- Basic filters.
- Contact Us submissions appearing in Inbox.
- Open a conversation.
- Reply.
- Reply All.
- Compose a new email.
- Forward.
- To.
- CC.
- BCC.
- Subject.
- Attachments.
- Draft autosave.
- Optional send later/scheduled send.
- Archive.
- Trash/delete policy appropriate to retention requirements.
- Delivery state where available.
- User/shop signature.
- Branded full-email preview.

Do not attempt to replicate Gmail/Outlook. Features such as complex labels, snooze systems, mailbox rules, @mentions, delegation workflows, or a general IMAP client are not required for the first product scope.

### 6.2 No AI writer in the shop Inbox

The Montreal Spider Co. reference currently contains an AI/prompt-oriented compose helper. GarageOS should **not** include that behavior as part of this scope.

The garage writes its own message. GarageOS provides the shop branding, sender identity, signature, rendering, transport, logging, and customer context.

### 6.3 Contact Us integration

If the GarageOS-hosted shop presence/landing contains a contact form:

```text
Customer submits Contact Us
        ↓
Store inbound customer message
        ↓
Create/update Inbox conversation
        ↓
Associate Client when safely resolvable
        ↓
Notify authorized shop staff
        ↓
Optional branded acknowledgment to customer
```

A shop employee should be able to reply directly inside GarageOS and keep the history in the same conversation.

### 6.4 Customer and business context

Where possible, the conversation view should surface or link relevant GarageOS context:

- Client.
- Vehicle(s).
- Appointment(s).
- Quote(s).
- Work order(s).
- Invoice(s).

Do not duplicate these entities inside Communications. Store relationships/references.

### 6.5 Timeline / relationship history

A useful customer communication timeline may include both human conversation and important automated activity, for example:

```text
Sep 12  Marc: "Can I bring the car tomorrow?"
Sep 12  Sarah replied
Sep 14  Appointment confirmation sent ✓
Sep 15  Appointment reminder SMS delivered ✓
Sep 16  Quote Q-1042 sent ✓
Sep 16  Quote approved
```

Automated events do not necessarily need to render as chat bubbles, but they should be observable in customer communication history.

## 7. Inbound email: what makes the Inbox real

Outbound email alone is not a true Inbox.

To allow a customer to reply to a GarageOS-managed address and have the message appear inside the shop's Inbox, GarageOS needs an inbound-email pipeline.

At implementation time, research the current provider capabilities and select the simplest reliable inbound path. Do not assume outbound Resend configuration alone provides a hosted mailbox.

Likely requirements:

- Inbound-capable domain/address configuration.
- Provider inbound webhook/event.
- Webhook signature validation.
- Tenant/address resolution.
- MIME/text/HTML parsing.
- Sanitization.
- Attachment handling.
- Spam/abuse controls.
- Thread matching.
- `Message-ID`, `In-Reply-To`, and `References` handling where available.
- Safe storage.
- Idempotent webhook processing.

GarageOS Inbox is an **application-level customer communications inbox**, not necessarily a general-purpose IMAP/SMTP mailbox product.

## 9. Automations: operational customer communication

Automations are known GarageOS business events, not a generic Zapier clone.

Examples:

```text
APPOINTMENT_CREATED
APPOINTMENT_RESCHEDULED
APPOINTMENT_CANCELLED
APPOINTMENT_REMINDER_DUE
QUOTE_SENT
QUOTE_ACCEPTED
QUOTE_REJECTED
WORK_ORDER_STATUS_CHANGED
VEHICLE_READY
INVOICE_ISSUED
INVOICE_PAID
INVOICE_OVERDUE
SERVICE_REMINDER_DUE
```

Each shop should be able to control appropriate combinations of:

- email enabled/disabled;
- SMS enabled/disabled;
- timing;
- sender identity/route;
- localized template;
- plan-allowed customization.

Preferred reliability pattern:

1. Persist the business transaction.
2. Persist communication intent/outbox atomically where practical.
3. Process communication independently.
4. Record provider result.
5. Retry transient errors safely using idempotency.

A temporary provider outage must not roll back an invoice, appointment, or quote.

## 10. Templates

GarageOS should ship high-quality defaults, especially EN/FR, so a garage can use Communications without writing copy.

Conceptual model:

```text
CommunicationTemplate
  id
  shopId?
  channel              EMAIL | SMS
  key                  APPOINTMENT_CONFIRMATION | ...
  language
  subject?
  body
  isEnabled
  isSystemDefault
  createdAt
  updatedAt
```

### 10.1 Controlled variables

Allow whitelisted variables such as:

```text
{{customer.firstName}}
{{shop.name}}
{{vehicle.year}}
{{vehicle.make}}
{{vehicle.model}}
{{appointment.startsAt}}
{{quote.number}}
{{invoice.number}}
{{invoice.total}}
{{document.url}}
```

The allowed variable set should depend on event/template type.

Unknown or unavailable variables should fail validation before save/send instead of silently rendering broken text.

### 10.2 Template HTML safety

Do not let tenants inject arbitrary executable HTML/JS.

Prefer safe structured content or sanitized markup rendered inside GarageOS's shared email layout.

### 10.3 Free-form human email vs templates

Inbox compose/reply is human-authored free-form content rendered inside the branded layout.

Operational automations use product templates.

Campaigns may use a campaign editor but must still render through the common shop branding/compliance system.

## 11. Campaigns / Newsletter

Campaigns are a formal part of GarageOS Communications, not a note for some distant future.

The product goal is that a typical shop can handle legitimate customer newsletters, seasonal outreach, reactivation, and service campaigns using the customer/vehicle/service data GarageOS already owns instead of exporting lists to an external newsletter tool.

A reasonable marketing claim later is:

> **Email campaigns built in — no separate newsletter tool required.**

Do not make competitor-specific claims in product UI unless separately approved.

### 11.1 Campaign flow

Target UX:

```text
Create campaign
    ↓
Choose audience / segment
    ↓
Choose channel(s)
    ↓
Write message
    ↓
Preview branded result
    ↓
Send test
    ↓
Schedule or send now
    ↓
Track delivery / failures / unsubscribes
```

### 11.2 Audience / segmentation

GarageOS can provide much more useful segmentation than a generic mailing list because it knows clients, vehicles, appointments, and service history.

Potential segments:

- All marketing-consented customers.
- Active customers.
- Customers inactive for X months.
- Language = EN / FR.
- Vehicle make/model/year ranges.
- Customers with relevant service history.
- Customers due/likely due for a service reminder.
- Seasonal tire customers.
- Customer-created/manual selection.
- Future saved segments.

Do not implement dangerous arbitrary SQL/filter expressions from tenants.

### 11.3 Audience snapshot

At send/schedule time, preserve enough information to know who was targeted/eligible.

Do not rely only on a live query whose results may change after the campaign is sent.

Use a recipient/audience snapshot or equivalent immutable campaign-recipient records.

### 11.4 Draft / preview / test / schedule

Campaigns should support:

- Draft.
- Branded preview.
- Test email to authorized shop addresses.
- Send now.
- Schedule using the shop timezone.
- Cancel scheduled campaign before processing begins when safe.

### 11.5 Metrics

At minimum, where provider data supports it:

- recipients;
- queued;
- sent;
- delivered;
- bounced;
- failed;
- unsubscribed.

Open/click tracking should only be included if it is technically reliable enough and appropriate under the privacy/product policy chosen at implementation time.

### 11.6 Email and SMS campaigns

Email campaigns can be broadly available subject to plan/volume limits.

SMS campaigns have meaningful provider cost and additional consent/compliance risk, so entitlement, pricing, and legal requirements should be stricter.

## 12. Transactional vs marketing consent

GarageOS must treat operational/transactional communication separately from marketing.

Conceptual customer preference/consent information may include:

```text
preferredLanguage
preferredChannels
marketingEmailConsent
marketingSmsConsent
consentSource
consentAt
emailMarketingOptOutAt
smsMarketingOptOutAt
```

Exact legal semantics must be validated for supported jurisdictions. Do not treat these field names as legal conclusions.

### 12.1 Marketing unsubscribe

Every marketing email/campaign must include the required unsubscribe mechanism and sender/business identification.

The unsubscribe/compliance portion should be injected by the shared renderer and must not be removable by editing campaign body text.

### 12.2 Transactional messages

Do not add a generic marketing unsubscribe link to critical transactional emails in a way that lets a customer accidentally disable necessary service communications.

Product/legal design must distinguish these categories appropriately.

### 12.3 Suppression lists

Hard bounces, complaints, and marketing opt-outs should create appropriate shop-scoped/global-safety suppression records so GarageOS does not repeatedly send bad mail.

A campaign send should deduplicate recipients and check suppression/consent before queueing provider sends.

Provider STOP/START and equivalent SMS events must synchronize back into GarageOS where applicable.

## 13. Email composition basics

The GarageOS Inbox should support the basic conventions users expect from email without trying to become Outlook.

Required/target fundamentals:

- To.
- CC.
- BCC.
- Reply.
- Reply All.
- Forward.
- Subject.
- Attachments.
- Signature.
- Drafts/autosave.
- Send now.
- Send later where supported by the outbox scheduler.

### CC/BCC

The provider adapter and GarageOS message model must carry CC/BCC properly.

BCC recipients must not be exposed to other recipients in rendered headers/history visible externally.

### Reply All

Reply All should compute recipients from the inbound message while avoiding obvious duplicates and the shop's own receiving identities.

### Attachments

Enforce:

- allowed/safe MIME types;
- size limits;
- malware/security considerations appropriate to deployment;
- tenant-scoped storage authorization;
- provider attachment limits.

A useful future enhancement is selecting GarageOS-native documents such as an invoice/quote as an attachment, but do not block the base Inbox on that convenience feature.

## 14. Email provider architecture

Resend is the preferred current outbound provider, subject to re-verification of current capabilities at implementation time.

Provider-specific logic should sit behind a small adapter/service boundary.

### 14.1 GarageOS-managed provider account

Recommended default for normal customers.

Benefits:

- low-friction onboarding;
- no customer API keys;
- central billing/usage;
- easy subscription bundling.

Risks:

- shared reputation;
- aggregate rate limits;
- tenant abuse can damage the platform;
- strong platform-side throttles/suppression are required.

### 14.2 BYOK / shop-owned provider

Possible future advanced/enterprise feature.

Do not make this the normal onboarding flow.

### 14.3 Inbound provider capability must be researched separately

Do not conflate outbound Resend delivery with inbound hosted-email behavior.

Before Inbox inbound implementation, verify current provider support for receiving/parsing email, MX/DNS requirements, attachment handling, event signatures, threading metadata, and pricing.

If another inbound provider is operationally better, keep the application model provider-agnostic.

## 15. SMS architecture

Twilio is the preferred current SMS provider.

GarageOS acts as an ISV sending on behalf of independent shops. The target architecture should consider provider-level isolation such as a Twilio subaccount per shop and appropriate Messaging Services/numbers.

Conceptually:

```text
GarageOS Twilio parent
  ├── Shop A subaccount → messaging service / number
  ├── Shop B subaccount → messaging service / number
  └── Shop C subaccount → messaging service / number
```

Benefits:

- usage attribution;
- operational isolation;
- easier compliance containment;
- future dedicated shop number;
- future two-way SMS Inbox.

Do not provision paid provider resources during random page loads. Provision intentionally, idempotently, and with recoverable status.

**Implementation status:** implemented as one subaccount + one number per shop (no Messaging Service yet), provisioned only by GarageOS from `/platform`, with a 30-day release lifecycle, inbound/two-way SMS in the Inbox, delivery status and STOP handling. See `docs/notifications.md` → "SMS por taller".

Do not hardcode US-only assumptions into Canadian shops. Model provider/compliance metadata so region-specific requirements can evolve.

## 16. Unified Inbox direction: email first, SMS compatible

The first serious Inbox can be email-led, but the thread/message abstraction should allow SMS to appear in the same Communications area later.

Example:

```text
Customer email → thread
Garage reply    → same thread
Appointment reminder email → activity
Reminder SMS             → activity
Customer SMS reply        → thread activity / conversation
```

Do not force different customer identities into one thread unless GarageOS can resolve them safely.

The UI may visually distinguish channels.

## 17. Documents remain business entities

Invoices, quotes, receipts, and work-order documents are GarageOS business entities/documents. Email/SMS are delivery channels.

Desired pattern:

```text
Invoice finalized
    ↓
Persist business/document state
    ↓
Generate/secure PDF or customer URL
    ↓
Queue communication
    ↓
Deliver by email/SMS
```

A provider failure must not make the invoice cease to exist.

Use authenticated or appropriately tokenized/expiring access for sensitive documents rather than permanently public storage links.

## 18. Communication usage ledger

Track provider/billable usage separately from document state.

Conceptual:

```text
CommunicationUsage
  shopId
  messageId
  channel
  provider
  units
  providerCost?
  customerBillableUnits?
  billingPeriod
```

Email may count one message or another provider-defined unit.

SMS should track provider billing segments/units accurately.

Money values must use decimals/smallest currency units consistently, never floating point.

## 19. Plans and entitlements

Communications should exist across paid GarageOS plans rather than having a "no email" starter product.

Exact pricing/limits are intentionally TBD.

Possible product framing:

```text
Starter
- GarageOS managed sender
- Branded transactional email
- Basic Inbox
- Essential automations
- Limited sender identities/aliases
- Small included SMS allowance
- Basic campaign allowance

Pro
- More sender identities
- Custom sending domain
- Editable templates
- More automations
- Larger campaign limits
- Larger SMS allowance
- More branding controls

Business
- Higher limits
- Advanced permissions/routing
- Future multi-location communication controls
- Advanced reporting/inbox capabilities
- API/integration capabilities
```

Do not commit these exact feature gates until pricing/product decisions are made.

### 19.1 Central entitlement layer

Do not scatter plan checks across unrelated modules.

Create/extend a central layer capable of questions such as:

```text
canSendEmail(shop)
canUseInbox(shop)
canSendCampaign(shop)
canSendSms(shop)
canUseCustomDomain(shop)
canCreateSenderIdentity(shop)
maxSenderIdentities(shop)
monthlyEmailAllowance(shop)
monthlyCampaignAllowance(shop)
monthlySmsAllowance(shop)
```

Exact naming is implementation-defined.

Every send path should evaluate both:

- user/shop authorization;
- product entitlement/quota.

Critical GarageOS account/security notifications must remain separate from tenant customer-message quotas.

## 20. Deliverability and abuse controls

Because GarageOS manages sending infrastructure, this is part of the product architecture, not an afterthought.

Build/plan for:

- per-shop send rate limits;
- campaign recipient limits;
- per-plan quotas;
- bounce handling;
- complaint handling;
- suppression;
- sender identity restrictions;
- custom-domain verification state;
- abnormal-volume detection;
- audit logs;
- platform ability to suspend a sender/shop communication capability without deleting business data;
- provider webhook verification;
- idempotency.

Campaign sending should be queued/throttled rather than launching uncontrolled bursts from a web request.

## 21. Permissions

Audit the existing GarageOS role system before defining new roles.

At minimum, sensitive actions should map intentionally to role/permission checks:

- create/rename sender identity;
- connect custom domain;
- change event routing;
- send campaigns;
- view customer conversations;
- send/reply as the shop;
- edit templates;
- modify consent/preferences where legally appropriate;
- view usage/billing.

Creating sender identities/custom domains should generally require stronger permission than simply replying to a customer from an already-approved identity.

Every query/mutation must be scoped by `shopId` derived from authenticated context, not trusted from arbitrary client input.

## 22. GarageOS platform mail vs shop customer mail

Keep these systems logically separate.

### GarageOS → Garage user

Examples:

- welcome/account verification;
- password/security;
- subscription/billing;
- trial/account notices;
- platform incidents.

These use GarageOS identity and branding.

### Shop → Shop customer

Examples:

- human Inbox messages;
- appointment confirmations;
- quote/invoice delivery;
- vehicle-ready updates;
- service reminders;
- campaigns.

These use the shop's communication identity, branding, consent rules, and usage ledger.

Do not mix sender identities, unsubscribe state, branding, quotas, or analytics between these domains.

## 24. Non-goals / guardrails

For this scope, GarageOS is **not** trying to become:

- Gmail/Outlook/Exchange.
- A general IMAP client for arbitrary existing mailboxes.
- A generic workflow automation builder.
- A cold-email blasting platform.
- An AI email-writing product.
- A fully featured marketing automation suite comparable to enterprise marketing clouds.

The product goal is narrower and stronger:

> **Give an independent garage the customer communication tools it actually needs, already connected to its clients, vehicles, appointments, quotes, work orders, invoices, and service history.**

## 26. Product acceptance principles

The implementation should be considered directionally correct only if these remain true:

1. **Changing a sender route changes the real sender used by the provider.**
2. **A shop can never use another shop's sender, messages, domain, customers, or provider resources.**
3. **Every customer email uses the shared branding/footer system.**
4. **Inbox replies and new emails are actually delivered through approved shop identities.**
5. **Contact Us can become a real shop conversation, not just an admin notification email.**
6. **Automations are business-event driven and do not corrupt the business transaction if delivery fails.**
7. **Campaigns use GarageOS customer/service data but respect consent, suppression, quotas, and throttling.**
8. **Marketing unsubscribe/compliance cannot be accidentally removed from a campaign template.**
9. **Provider dashboards are not the only place to understand message state/history.**
10. **GarageOS remains simpler than a general email client: enough for a garage to communicate professionally without leaving the platform.**
